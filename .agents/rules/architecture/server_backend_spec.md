# Server & Distributed Backend Specification

**Location**: `src/server/` & `src/backend/`
**Status**: Reverse-Engineered Spec (Brownfield)
**Date**: 2026-09-21

## 1. Overview
These components form the backbone of JasmineGraph's distributed execution model. The `server` component acts as the Master node orchestrator, while the `backend` and `JasmineGraphInstance` components run as daemon processes on the Worker nodes.

## 2. Core Architecture

### 2.1 Master Orchestrator (`JasmineGraphServer.h`)
* **Role**: The central coordinator. It spins up workers (`startRemoteWorkers`), assigns partitions to them, and maintains the global state of the cluster.
* **Communication**: Uses custom TCP/IP socket protocols to send commands to workers (e.g., `sendQueryPlan`, `initiateMerge`).
* **State Tracking**: Uses `hostPlaceMap` and `workerPortsMap` to route tasks to the correct physical machine.

### 2.2 Worker Daemons (`JasmineGraphInstance.h`, `JasmineGraphBackend.h`)
* **Role**: These processes run continuously on the worker machines. They listen on designated ports for instructions from the Master.
* **File Transfer**: Uses `JasmineGraphInstanceFileTransferService` to receive partition files generated by the Master's `MetisPartitioner`.
* **Execution**: When a query plan is received, it triggers local executors (like `IntraPartitionParallelExecutor`) and sends the results back.

## 3. Deployment Modes: Docker Mode vs Kubernetes Mode

JasmineGraph supports two primary deployment topologies defined by `jasminegraph_profile` (`globals.h`):

### 3.1 Docker Mode (`PROFILE_DOCKER`)
* **Entrypoints & Scripts**: `run-docker.sh`, `start-docker.sh`, `test-docker.sh`, and `docker-compose.yml`.
* **Worker Lifecycle**:
  * Master runs with access to the Docker daemon (`/var/run/docker.sock`).
  * In `startRemoteWorkers`, the master launches worker containers directly on the local engine (`docker run`) or remote hosts over SSH (`docker -H ssh://<host> run`).
  * Containers attach to a unified bridge network (`jasminenet`, `172.28.5.0/24`) and mount shared data folders for partition files, temporal snapshots, and logs.
* **Supporting Services**: Observability (Prometheus, Pushgateway, Grafana, Loki, Alloy, Tempo) and auxiliary data stores (Kafka, HDFS, Ollama) are configured alongside JasmineGraph in `docker-compose.yml`.

### 3.2 Kubernetes Mode (`PROFILE_K8S`)
* **Controller Architecture**: Handled programmatically via `K8sWorkerController.h` and `K8sInterface.h` using the official C Kubernetes API client.
* **Resources & Declarative Specs (`k8s/`)**:
  * **Master**: Deployed via `k8s/master-deployment.yaml` with a dedicated Service `jasminegraph-master-service` (`k8s/master-service.yaml`).
  * **Dynamic Workers**: When the master starts or scales, `K8sWorkerController::spawnWorker` creates individual `v1_deployment_t` instances (`jasminegraph-worker<id>-deployment`), services, and dedicated storage (`v1_persistent_volume_t` / `v1_persistent_volume_claim_t`).
  * **Configuration**: Centralized in `ConfigMap` `jasminegraph-config` (`k8s/configs.yaml`), managing Prometheus endpoints, `MAX_WORKER_COUNT`, and autoscaling flags.
* **Elastic Scaling**: `K8sWorkerController` implements `scaleUp(count)` and `scaleDown(workerIds)`, querying node availability and synchronizing worker records in `MetaDB`.

## 4. Implicit Contracts & Constraints (Important for AI Agents)
* **Non-Blocking Network Calls**: The socket communication in `JasmineGraphServer` is synchronous in many places. AI agents must be extremely careful not to introduce long-running compute loops on the main network threads, as it will cause cluster-wide timeouts.
* **Port Management**: Workers use distinct ports for control commands versus bulk data transfer (`workerPortsMap` vs `workerDataPortsMap`). Agents must not mix these up.
* **Stateless Workers**: Workers should generally be treated as stateless compute engines. The definitive truth of the cluster lives in the Master's `MetaDB`.
* **Deployment Profile Consistency**: Never hardcode container engine commands without checking `jasminegraph_profile`. Behavior must cleanly branch between Docker socket CLI spawning and Kubernetes declarative API interactions.
